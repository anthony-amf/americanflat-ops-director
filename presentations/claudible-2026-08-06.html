01 / Skills registry

Nothing syncs the registry automatically. That is the catch.

The skill repo and the registry entry are two different gates. Since 8 July you can commit straight to main on your own skill — but the registry stays Governor-gated. Bump a version without flagging it and the entry quietly goes stale.

At 127 skills nobody can eyeball that. Two problems are already in the snapshot:

  • Three live skills still carry a sub-1.0 version. skill-log-notion 0.0.1 · skill-yusen-invoice-processor 0.1.0 · skill-casepack-xref 0.2.0. In use, but the registry calls them pre-release — the version drifted from the tag.
  • Four entries were provisioned and never published. Three have sat since early May. One is a smoke test whose own description says it is safe to delete.

The ask

When you change a published skill, post it in #ai-github-skills and tag the Governors — version, and whether the description changed. It is two lines. It is the only thing keeping the registry honest.

Worth deciding

Do we clear the four stale provisioned entries, and reconcile the three sub-1.0 versions against their tags? Both are small jobs now and annoying jobs at 250 skills.

02 / Frame OS

An interface for agents, not another agent.

“FRAME.OS should be the interface / front-end where we can see and execute this, a lot of work pending on the backend to make this real.”

Iván Calderón · #operations-team-information-channel · 18 June

“Our plan for the next 90 days in AI is focused on Frame.OS (Agentic AI) and automating our more complex processes — mostly the ones that deal with money.”

Kent Nunez · #operations-team-information-channel · 18 June

The problem it is meant to solve

Today an agent runs and the only evidence is a Slack post or a file in Drive. If it did the wrong thing we find out downstream; if it did nothing, maybe never. Frame OS answers four questions about any agent:

  • What did it do?A record of actions, not just outputs.
  • Did it work?Performance against what it was meant to achieve.
  • What did it cost?Tokens and compute, per agent, per run.
  • Should it be allowed to?Approval before the risky steps, not after.
Definition

02 / Frame OS

The model is Cake: a bakery that runs on one app.

Cake is the internal operating system of a bakery business. One web app whose home screen is a launcher organised by business function — not a chat window with tools bolted on the side.

  • AI Agents — seven named assistants, each with a face and a job title My Agent (personal) · Sam (bakery scheduling) · Phyllis (finance) · Jamie (payroll) · three more
  • Then the apps — fourteen of them, grouped by function Operations (8) · Safety & Quality (4) · People & Finance (2)

The agents are listed first — the assistant is the front door, the apps are what it reaches through.

How it reached us

  • 9 Apr Kent contacts Cake's builder“to see if I can learn from him”
  • 29 Apr Anthony shares the Cake demoSent to Iván “for reference” the week Kent was prepping the automation share
  • 5 May Giorgio asks directlyHe had heard of a company run entirely on agentic AI, and asked how AF is setting up for it

Why “Frame”

Cake sells cake. We sell frames — and the job is literal. Iván uses exactly that word: frame the Data Analyst agent into a system that shows its actions and performance.

The Cake inspiration

02 / Frame OS

Four things in the demo worth copying exactly.

An operator asks Eva to rebuild a weekly maintenance report out of Odoo and post it to a team channel. All four are visible on screen while she works.

  • 1 · Permission mode is a switch on the agent. Read Only · Normal · Power in the header. We already hold this data — every registry entry declares an action tier. Cake makes it a live control, not a metadata field.
  • 2 · Every step is a named tool with a duration. Querying Odoo 21ms · Testing code tool 423ms · maintenance-weekly-report 3 mins. Nothing is a black box.
  • 3 · Approval gates explain themselves. A card appears before it fires: “Post a message to a Zoho Cliq channel, sent from your dedicated bot.” You approve the described action, not a function name.
  • 4 · Failures are shown, not swallowed. The demo's own post failed — HTTP 400 — and the UI printed it. An agent you cannot see failing is one you cannot trust.

And one thing to argue about

Eva did not use a report tool — she built one: Creating code tool → Testing code tool → Updating code tool, then runs it. Ours are human-authored, reviewed and Governor-gated. Theirs is faster; ours is auditable. Where Frame OS sits on that line is the real design question.

Honest status: one agent, foundations drafted, front end not built.

What is real

  • The pilot agent works.The Data Analyst bot reaches every BigQuery table and has a knowledge base, so it can learn what it does not know.

  • It is on the 90-day list.Alongside Canada, DF with ATS, closing SC, POD and Walmart 3P.

What is not

  • No front end yet.The interface Iván describes — see and execute — does not exist. The biggest piece of work.
  • No observability backend.Nothing records what an agent did, whether it worked, or what it cost.
  • One agent is not a fleet.Only worth building if several agents run unattended. Today: one bot and some routines.
  • Build-vs-adopt is unresolved.Some of Frame OS may arrive off the shelf. Worth deciding deliberately, not by default.
Status

Both halves

This is why last Claudible was about GitHub.

Frame OS can only see what is in the registry. A skill living on someone's laptop is invisible to it — it cannot be versioned, tiered, called by an agent, or watched.

That is the whole argument for pushing to GitHub, and it is not an administrative preference. It is a prerequisite. Every skill that stays local is a capability the company does not actually own and a future agent cannot use.

127 live skills is the asset. The registry is the inventory. Frame OS is the control room. They are one project, in that order.

Put another way

Every skill we publish makes Frame OS more worth building. Every skill we keep local makes it less.

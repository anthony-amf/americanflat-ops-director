# Changelog

All notable changes to `skill-fixer` will be documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.19.0] — 2026-07-09

**Derives the GitHub handle in Step 3 instead of asking for it.** The submit step used to ask the Builder to type their GitHub username — the field whose mistyping (Carolina, 2026-05-20) surfaced downstream as a misleading 403 and cost hours of misdiagnosis. Since Americanflat's machines authenticate `gh` (and sign commits) as the shared org account, that value is available live and reliable.

- **Step 3.2 now derives and confirms.** It runs `gh api user --jq .login`, shows the result for a one-tap `ok`, and only runs the syntax + `gh api users/<handle>` existence check when the Builder types a *different* handle (the case that can actually be wrong). A single `ok` is the common path; a typed override keeps the full validation; an unauthenticated/offline `gh` falls back to the old ask-and-validate flow. You can't mistype a value you don't type.
- **The audit handle is `americanflat-code`.** Ivan confirmed the intended submission identity is the shared org code account (what `gh api user` already returns on the machine), not a personal handle — the older `ivan-calderon-af` example was stale. Recorded so the derive-and-confirm default is grounded in the real account.
- **Backwards compatible.** A Builder whose `gh` resolves sees one confirmation instead of a blank prompt; the validation that catches a bad *typed* handle is unchanged. Steps 1–2 and every other Step 3 gate are untouched.

## [0.18.0] — 2026-07-09

**Reshapes the whole Builder experience from six stages into three steps — Confirm → Apply → Submit — and moves all the compliance machinery off the Builder's screen.** A live test of the earlier six-stage flow (on `amf-amazon-vc`) showed the real problem wasn't *what* Skill Fixer decided but *how much it said*: a wall of justification text, internal jargon (`Bucket A/B/C/D`, `^skill-[a-z0-9-]+$`, raw TOML keys, "standalone mode"), and a "gather B" phase that asked six questions one at a time. This release rebuilds SKILL.md around what the Builder actually does, and demotes every rule to a Claude-only reference.

This supersedes and folds in the reverted work from commit `d5cdb48` (the shipped-then-reverted v0.15–v0.17: tier classification, propose-not-ask department/changelog, and the first UX pass). Those ideas are kept; their *presentation* is replaced.

- **Three Builder-facing steps.** **Step 1 Confirm** fuses the old Pre-flight + discovery + plan + gather-B into one screen: a plain "I'll set these up for you" summary plus a single **pre-filled form** the Builder answers in one reply (`ok`, or fix a line). **Step 2 Apply** makes the changes and shows a plain "done" list. **Step 3 Submit** (opt-in) is the old Stage 6, unchanged in its gates. A fix-only run is two steps; fix-and-submit is three.
- **One form, not six questions.** Everything inferable is pre-filled for a one-tap confirm — description drafted from the skill's own content, department best-fit-guessed from the closed set, tier classified from what the skill reads/writes, changelog drafted from the fixes that land, version defaulted to `0.1.0` for a new skill. **Owner is the only blank** (the one fact only the Builder knows), until the identity-memory feature lands.
- **Consent on a summary; diff on demand; force-show only edits to the Builder's own words (Principle #1 relaxed).** Scaffolded files and inferred settings apply on the plain-language summary consent — no forced diff for content the Builder can't meaningfully review. `show me` reveals the exact diff of anything; and any fix that rewrites *their* prose (e.g. trimming their description) always shows the before/after and takes a yes on that specific change. Nothing writes without consent; git keeps it reversible. This preserves every protection the old forced-diff rule provided (no silent edits, human in the loop, full inspectability) without the wall of diffs.
- **Internal taxonomy left the screen.** Findings are still classified — now as I-fix / Ask-you / Governor / Note internally — but the Builder sees "I'll set these up," "confirm these," "this needs a Governor," and "a couple of notes for later." No bucket letters, no ADR clause numbers, no regexes. `why?` surfaces the reasoning on demand; `help` / `show me` / `abort` work anywhere.
- **All the rules survive, relocated.** The name-normalization algorithm, `.env.example` derivation, the ≤350-char description rule, conditional `language`/`python`, tier classification, department/changelog handling, the manifest-vs-reality checks, the security escalations, the D1/D2/D3 advisories, and the full Step 3 git/Slack machinery (readiness check, `gh api users` handle validation, `github-americanflat` alias, branch format, subteam Slack post, same-session threading) all live in a **"Checks reference" section the Builder never sees.** Nothing was dropped; it moved.
- **Tier 3, security, and Slack/push gates unchanged.** Trust-level-3 still stops for explicit confirmation and names the three safeguards + two-Governor rule; security findings still escalate and are never patched; Step 3's `go` and `send` approvals are intact. The Publisher's independent blind tier call is untouched (Skill Fixer still never edits `skill-publisher-framework`).
- **Rationale for the version.** Jumps 0.14.0 → 0.18.0 to stay monotonically above the pushed `v0.17.0` tag from the reverted line; 0.15–0.17 were shipped and reverted the same day and are intentionally not re-listed as separate entries.

## [0.14.0] — 2026-06-09

**Auto-fixes a non-conforming `[skill].name` instead of asking.** `af-skill-admin create` (the 🚀 promote step) requires the skill name to match `^skill-[a-z0-9-]+$`, but `publisher-review.yml`'s deterministic checks only verify that the `SKILL.md` and `skill.toml` names *agree* — never the regex. So a mis-prefixed name passes review clean and dies at promote. Until now Skill Fixer flagged the name as **Bucket B** (ask the Builder), which only helps if the Builder runs Skill Fixer *and* acts on the prompt — neither of which happened for the `daily-briefing` candidate (named `daily-briefing`, no `skill-` prefix), whose promote failed on 2026-06-09 with `Invalid skill name`.

- **Name conformance moved Bucket B → Bucket A.** The `skill-` prefix and kebab-case are mandatory *format*, not a naming *choice* — the Builder still owns the meaningful stem; Skill Fixer just enforces the wrapper. A non-conforming `[skill].name` (or `SKILL.md` frontmatter `name`) is now auto-normalized and applied in the Stage 4A mechanical batch, so it gets fixed even when the Builder blasts through `apply all`.
- **Deterministic normalization algorithm.** (1) lowercase; (2) every run of non-`[a-z0-9]` → a single hyphen; (3) collapse/trim hyphens; (4) repeatedly strip a leading `skill-` or redundant company prefix (`af-`, `amf-`, `americanflat-`); (5) prepend one `skill-`. The same value is written to both `skill.toml` and `SKILL.md`. Examples: `daily-briefing` → `skill-daily-briefing`, `af-940-validator` → `skill-940-validator`, `Skill_Foo` → `skill-foo`.
- **Guarded fallbacks stay Bucket B.** If stripping prefixes leaves an empty stem (nothing to build a name from), Skill Fixer asks the Builder and validates the answer against the regex. A genuine *disagreement* between two individually-valid-but-different names also stays a Builder question (which is canonical?).
- **Folder-name check relaxed.** Skill Fixer never renames folders, and the manifest is authoritative (Stage 6 derives the branch from `[skill].name`), so a folder/manifest mismatch after normalization is a non-blocking note, not a finding with no fix.
- **Touched:** Stage 1 (Bucket A/B lists), Stage 1B (`skill.toml` schema rule + the algorithm, `SKILL.md`-shape rule, Bucket B list, folder-name check), Stage 2 example plan, Stage 3 (removed the name question), Stage 4A/4B, and the Failure quick-reference.

## [0.13.0] — 2026-06-09

Adds the missing **`requires_secrets` ⇒ `.env.example`** check. `skill-publisher-framework` blocks any candidate where `.env.example` is present if-and-only-if `requires_secrets = true` (and its malicious-prompting scan requires every env var a script reads to be declared there), but no stage of Skill Fixer ever checked for it. A secrets-bearing skill could pass standalone pre-flight clean and still get sent back by the Publisher, and on remediation Skill Fixer had no rule to regenerate the file — so the finding survived a fix-and-resubmit cycle. The `daily-briefing` candidate hit exactly this on 2026-06-09: flagged for a missing `.env.example`, resubmitted through Skill Fixer, still missing it.

- **New Bucket A check (standalone, Stage 1B).** When `skill.toml` declares `requires_secrets = true` and no `.env.example` exists, Skill Fixer reads every `.py` file, collects each variable referenced via `os.getenv` / `os.environ[...]` / `os.environ.get(...)`, and scaffolds `.env.example` with those names and empty values under a `# Copy to .env …` header. Real secret values are never written; a non-secret literal default the script supplies (e.g. `os.environ.get("PLAID_ENV", "production")`) may be carried over as a hint. The new file lands through the normal Stage 4A apply flow, which already prints full new-file content before writing.
- **Falls back to Bucket B when it can't derive.** If `requires_secrets = true` but no env reads exist (the secret may flow through an MCP connector, or the flag is wrong), Skill Fixer asks the Builder which variables belong — it does not invent them. The inverse mismatch (`requires_secrets = false` but a `.env.example` is present) is also Bucket B: ask whether to drop the file or flip the flag.
- **Remediation path covered too (Stage 1).** A review-report "`.env.example` missing" finding is now explicitly classified as Bucket A (regenerated from the scripts' env reads) rather than relying on the report's wording to carry the variable list, so a Publisher send-back for this reliably gets fixed on the next run.
- **Manifest-vs-reality + Failure quick-reference updated** with the new `requires_secrets`/`.env.example` consistency rows.
- **Backwards compatible.** Candidates that already ship a correct `.env.example` (or declare `requires_secrets = false` with no file) see zero new findings. Buckets C/D are unchanged.

## [0.12.0] — 2026-06-04

Adds **`[skill].department` to Bucket B** so the manifest's department is gathered from the Builder instead of silently defaulting. Department flows into the registry at promote (`promote.py` reads `[skill].department` from `skill.toml`, defaulting to `ops` if absent, and passes it to `af-skill-admin create --department`), but until now no stage of Skill Fixer ever checked or asked for it — a candidate could pass clean with no department and land in the registry as `ops` by accident, and an off-list value would pass pre-flight only to fail at promote.

- **New Bucket B check — `[skill].department`.** Flagged when the field is missing, `TBD`, or not one of the six valid departments (`ops`, `sales`, `marketing`, `finance`, `pd`, `exec` — the `DEPARTMENTS` set `af-skill-admin create` enforces). Added to the remediation-mode Bucket B list (Stage 1) and the standalone-mode Bucket B list (Stage 1B). The fix lands in `skill.toml [skill].department` via the standard Stage 4B apply flow.
- **Stage 3 prompt + closed-set validation.** Because department is a fixed enum (unlike tier, which Skill Fixer must never pick for the Builder), Stage 3 presents the six values and lets the Builder choose, then validates the answer is exactly one of them — a deliberate per-field exception to the "do not validate beyond format" rule, mirroring the existing `[skill].name` regex check. An off-list answer re-shows the list and re-asks.
- **Why now.** Department was the one manifest field that reaches the registry but was neither in Bucket A's required-key presence check nor Bucket B's value-gathering, so it relied entirely on the Builder having hand-typed it correctly into `skill.toml`. Catching it at the Builder's desk closes the same passes-review-fails-at-promote gap the name and description rules already guard against.
- **Backwards compatible.** Candidates that already declare a valid `[skill].department` see zero new findings. Buckets A/C/D are unchanged.

## [0.11.0] — 2026-06-04

Extends Bucket D with a third advisory check: **BigQuery/GCP authentication via a service-account key file**. Like the path checks, it's flag-only — Skill Fixer never edits the script — but it carries a hard guard so a *committed* key file escalates as a leaked secret instead of being downgraded to advice.

- **New Check D3 — service-account key file for BigQuery/GCP (shareability).** Flags scripts that authenticate by pointing at a service-account key (`service_account.Credentials.from_service_account_file(...)`, `*.from_service_account_json(...)`, or `GOOGLE_APPLICATION_CREDENTIALS` set to a `.json` key then used to build a GCP client). The key file is machine-local and won't travel with the skill, so a shared skill breaks on a teammate's machine. Skill Fixer recommends **one of two** Builder-chosen fixes: (a) document the dependency in the README (which key, where it goes, that the skill won't run without it), or (b) switch to `gcloud` / Application Default Credentials so each user authenticates with their own Google login (the pattern `skill-bq-schema-documenter` already uses). Flagged with `file:line` and a dedicated message template; offered for fix on a separate ask; never edited in the Stage 4 apply flow.
- **Hard guard against downgrading a leaked secret.** D3 is the *reference-by-path* case. If the service-account key file **itself** (a JSON with a `"private_key"` block) is committed in the candidate folder, that's a **Bucket C leaked secret** — Skill Fixer stops, refers by `file:line` only, and tells the Builder to ping a Governor with `secret-rotation-needed`. The standalone-mode "no systematic secret scan" note gains a narrow carve-out: if the D3 advisory scan *incidentally* lands on a committed key, don't walk past it — escalate that one finding. A Failure-quick-reference row codifies the C-not-D distinction.
- **Bucket D broadened** from "script portability & path hygiene" to "script portability, path & credential hygiene" across Stage 1, Stage 1B, Stage 2, and the README. Stage 2's plan example gains a D3 line; two Failure-quick-reference rows added (the D3 advisory and the committed-key escalation).
- **Why now.** Skills that read BigQuery with a bundled service-account key work fine for the author and then fail silently for anyone they're shared with — the exact "works on my machine" trap, but for credentials instead of paths. Catching it at the Builder's desk, as a one-sentence choice between "document it" and "use gcloud," is the cheapest fix, and keeping it flag-only means Skill Fixer never takes responsibility for rewriting someone's auth.
- **Backwards compatible.** Scripts that already use ADC / `gcloud` / `bq`, or that ship no `.py`, see zero new findings. Buckets A/B/C are unchanged; D1/D2 are unchanged.

## [0.10.0] — 2026-06-04

Adds **Bucket D — advisory script checks**: when a candidate ships `.py` files, Skill Fixer now flags two cross-platform/path-hygiene issues so the same skill behaves the same on a Builder's Mac and another's Windows. These are *advisory only* — flagged with `file:line` and a recommended fix, never rewritten inside the apply flow — which keeps Skill Fixer's "mechanical remediation, not redesign" character intact.

- **New Bucket D, defined in Stage 1B and referenced from Stage 1.** The scan runs in both modes whenever the candidate has any `.py` file (it's read-only). Two checks:
  - **D1 — Non-portable path construction.** Flags paths built with hardcoded OS separators (`"data\\out.csv"`) or string concatenation (`base + "/" + name`, `f"{base}/{sub}"`) instead of `pathlib.Path` / `os.path.join`. Recommends `pathlib.Path` with the `/` operator. Most relevant when `[compatibility].platforms` declares more than one OS. Guarded against false positives: `os.path.join`/`Path` usage, comments/docstrings/URLs/globs/regexes, and plain relative paths are not flagged (or flagged only lightly).
  - **D2 — Hardcoded machine-specific path.** Flags absolute, user/machine-specific path literals (`/Users/<name>/…`, `/home/<name>/…`, `C:\Users\<name>\…`, UNC `\\server\…`). Recommends moving the value to an environment variable (`os.getenv("VAR")`) documented in a gitignored `.env` plus a committed `.env.example`. Notes embedded-username privacy leaks but treats them as advisory, **not** a Bucket C secret. Guarded against `Path.home()` / `expanduser` / `tempfile` / `__file__`-relative paths.
- **Flag, never edit.** Per the owner's decision, Skill Fixer does not rewrite script code for a Bucket D finding — not even under `apply A` / `apply all`. Instead it uses a fixed message template that states the problem, recommends the fix, and **explicitly offers Claude as the fixer** on a separate ask ("ask me to *fix the path handling in `scripts/foo.py`* and I'll do it as a normal edit, outside the Skill Fixer flow"). A new "What you must never do" entry and two Failure-quick-reference rows codify this.
- **Stage 2 / Stage 4 / Stage 5 updated.** The plan shape gains a Bucket D group; the apply flow explicitly excludes C and D; the Stage 5 summary gains a "Script advisories (flagged, not edited)" line plus a closing nudge that the Builder can hand any advisory straight to Claude. The Stage 1B discovery summary now reports advisory count alongside mechanical / input-needed / security.
- **Scope guard updated, not abandoned.** The "Builder asks for improvements beyond the checklist → decline" rule stands; the two Bucket D advisories are named as the only bounded, advisory-only exception so Skill Fixer doesn't drift into a linter or redesign tool. The README's "what it does NOT do" section gains a matching carve-out.
- **Why now.** Builders run skills on a mix of macOS and Windows machines; a script that hardcodes `\` separators or a `/Users/<name>/…` path passes review and then breaks on a teammate's OS. Catching it at the Builder's desk — as advice they can act on in one sentence — is the cheapest fix, without making Skill Fixer responsible for (or capable of silently breaking) someone else's Python.
- **Backwards compatible.** Candidates that ship no `.py`, or whose scripts already use `pathlib`/`os.path.join` and machine-independent paths, see zero new findings. Nothing about Buckets A/B/C changes.

## [0.9.0] — 2026-06-03

Two Builder-experience refinements: **batch approval of mechanical fixes** in Stage 4, and **SSH host-alias normalization** in Stage 6's git operations.

- **Stage 4 now applies Bucket A (mechanical) fixes as one approved batch.** Previously every mechanical fix — a missing `.gitignore`, a CHANGELOG skeleton, a case-only rename, schema scaffolding — required its own `apply` / `skip`, so a Builder remediating a draft with several mechanical gaps clicked through the same prompt repeatedly. Stage 4 now shows all Bucket A diffs together, numbered, then takes a single decision: `apply all`, a subset (`apply 1,3`), an exclusion (`skip 2`), or `abort`. Every diff is still shown before anything is written — batching the *approval* never skips the *display*. Judgment fixes (Bucket B) remain per-item, and security findings (Bucket C) remain escalation-only; neither is ever batched. Stage 4 is split into **4A (Bucket A, batch)** and **4B (Bucket B, per-item)** to make the boundary explicit.
- **Critical Principle #1 and the "What you must never do" list updated** to scope the relaxation precisely: mechanical fixes may share one approval; judgment and security approvals never may; nothing is ever applied without its diff shown first.
- **Stage 6 git operations now use the `github-americanflat` SSH host alias, never raw `git@github.com:`.** Americanflat Builders authenticate to the org through a `Host github-americanflat` block in `~/.ssh/config` (pointing at `ssh.github.com:443` with the org-specific key). A raw `git@github.com:americanflat/...` URL uses the wrong identity and fails with `Permission denied (publickey)` (or silently authenticates as the Builder's personal account). The Stage 6.4 clone command is changed to `git@github-americanflat:americanflat/skill-candidates.git`, and a normalization rule is added: any `git@github.com:americanflat/...` URL encountered or constructed is rewritten to the alias before running. The README's install command already used the alias; this aligns SKILL.md with it.
- **Failure quick-reference + Stage 6.4 error notes updated.** The `Permission denied (publickey)` guidance now checks the host alias first (the most common cause) before pointing at the SSH key / `~/.ssh/config`.
- **Why now.** Both are friction the Builder hits on every run: the repetitive per-file clicking through mechanical scaffolding (raised directly by the owner), and the wrong-host clone failure that the README already worked around but SKILL.md still triggered.
- **Backwards compatible.** The batch decision is a superset of the old per-item flow — `apply 1` then `apply 2` style intent is still expressible via subset/skip — and the alias change only affects how the org repo is addressed, not what's pushed.

## [0.8.0] — 2026-06-01

Adds a `[skill].description` length/control-character check to Stage 1 discovery, closing a passes-pre-flight-fails-at-promote gap structurally identical to the one the v0.7.0 name check closed. Pairs with `af-skill-admin`'s companion change to `promote.py` (see that repo's CHANGELOG entry of the same date), which sanitizes the description defensively at the workflow layer.

- **Stage 1 now checks `[skill].description` is ≤ 350 chars with no control characters.** The `skill.toml` description is reused verbatim as the GitHub repo description by `af-skill-admin create` during promotion, and GitHub's `createRepository` mutation rejects anything over 350 chars or carrying newlines/tabs. A longer description passes pre-flight review but fails at promote — the same wasted-review-cycle gap the v0.7.0 handle check addressed, on a different field. Over-limit/control-char → **Bucket B** finding: Skill Fixer proposes a trimmed single-line ≤350-char candidate, the Builder approves the wording.
- **Bucket B description rule hardened against the "reuse" trap.** The SKILL.md frontmatter `description` (trigger matching, may run long) and the `skill.toml` description (the repo blurb, ≤350) are now explicitly distinguished. When a Builder asks to reuse the frontmatter description verbatim, Skill Fixer must measure it against 350 first rather than eyeballing it against the larger trigger-description budget — never silently truncate.
- **Why now — the `skill-monthly-invoice` candidate (2026-06-01).** Pre-flight passed, the Publisher approved, and promotion failed at `[1/5] Creating americanflat/skill-monthly-invoice` with GitHub's `createRepository` error: "Description control characters are not allowed, Description cannot be more than 350 characters." The 499-char description had been reused verbatim from the SKILL.md frontmatter during a prior Skill Fixer run; the explicit "ensure it respects the characters number limit" instruction was checked against the wrong (frontmatter-sized) ceiling because no codified limit existed at the description step. This change makes the binding 350-char limit a rule, not a judgment call.

## [0.7.0] — 2026-05-20

Hardens Stage 6.2's GitHub-handle validation to verify the handle actually exists on GitHub before encoding it into the candidate branch name. Pairs with `af-skill-admin`'s companion change to `promote.py` (see that repo's CHANGELOG entry of the same date) which derives `owner_gh` from the commit author instead of the branch-name segment as the primary source of truth — together they close a failure mode that cost hours of misdiagnosis on the first real promote attempt.

- **Stage 6.2 now runs `gh api users/<handle>` after the syntactic check.** A 200 means the handle resolves on GitHub and Stage 6.2 proceeds. A 404 means the handle doesn't exist; Skill Fixer rejects it with a clear error and re-prompts (this is the case the old check would have let through). Any other error (rate limit, network glitch, `gh` unauthenticated) is surfaced verbatim and the Builder is offered an explicit `confirm` bypass — better than blocking on a transient GitHub Status incident. The existing syntactic regex is tightened slightly to GitHub's documented rule (`^[A-Za-z0-9](?:[A-Za-z0-9]|-(?=[A-Za-z0-9])){0,38}$`) so the existence check isn't burned on values like `--leading-hyphen` or `trailing-hyphen-` that GitHub would reject anyway.
- **Failure quick-reference grew** with two new rows: one for the 404 case (the failure we're fixing) and one for the transient-error case (the new `confirm` bypass). Both rows reference the 2026-05-20 incident so future readers see the rationale, not just the rule.
- **Why now — Carolina's third promote attempt (2026-05-20).** Carolina typed `carolina-delrio-americanflat` at Stage 6.2 — her real handle is `carolina-delrio-amf` (404 on the typo). Stage 6.2's syntactic check accepted it (alphanumeric + hyphens, 30 chars), the branch name `skill-940-validator--carolina-delrio-americanflat--20260520` was built, and `promote.py` extracted the handle from the branch-name segment and passed it to `af-skill-admin create --owner-gh carolina-delrio-americanflat`. That step's third action — `PUT /repos/americanflat/skill-940-validator/collaborators/carolina-delrio-americanflat` — returned HTTP 403 "Resource not accessible by integration." GitHub returns 403 (not 404) when you try to add a nonexistent user as a collaborator on a private repo, masking the real cause as a bot-permissions problem. We chased that misdiagnosis through token-mint-timing analysis (`pattern_a_blueprint`'s "GitHub App installation tokens snapshot permissions at mint time" gotcha) and a re-grant of `administration: write` before noticing the handle returned 404 on `gh api`. Catching the typo at Stage 6.2 — at the moment the Builder types it, with the Builder still on the keyboard — is the cheapest possible recovery (~30 seconds, one re-prompt).
- **Why both layers.** Stage 6.2's check is the Builder-facing layer; `promote.py`'s commit-author derivation (af-skill-admin v0.7.0 companion) is the workflow-facing belt-and-suspenders layer. Either alone would have prevented the 2026-05-20 incident in some configurations; both together close the gap even when one layer is bypassed (e.g. a Builder submits a candidate manually without running Skill Fixer, or `gh` is unauthenticated in the Builder's environment and they `confirm` past the existence check anyway). Commit-author is the right primary source because it's whatever GitHub itself attributes the commit to via the email-on-the-commit lookup — the handle the Builder typed at Stage 6.2 is a label, not a fact.
- **Backwards compatible.** Builders whose handle resolves on GitHub see no behavior change beyond a short `gh api users/...` call (sub-second on a normal connection). The new prompts only surface when the handle is wrong or the existence check itself errors — both rare and both currently silent failures upstream of the real diagnostic surface.

## [0.6.0] — 2026-05-20

Two coordinated refinements to Stage 6's review-thread behavior: **per-trigger-message idempotency** in the CI workflows that the Slack reactions fire (see `af-skill-admin`'s v0.6.0 CHANGELOG for the workflow-side change), and **same-session single-thread consolidation** of every submission and remediation for a given skill. Together they make the audit trail one cohesive conversation per skill lifecycle (within a session), and make the 🔍 / 🚀 reactions safe to re-apply (e.g. accidentally un-reacted and re-reacted, or two reviewers reacting in quick succession).

- **Stage 6 threads remediations automatically — no Builder prompt.** When Stage 6.6 sends its first Slack message in a session, the channel ID and the returned message `ts` are captured in session context. Any subsequent Stage 6 invocation in the same Claude Code session (e.g. Publisher sends back, Builder runs Skill Fixer remediation, Stage 6 fires again) reuses both — the second post lands as a threaded reply under the first, with no Builder question, no permalink to paste, no mode toggle. Skill Fixer already has the thread coordinate the moment it posts the original message; consolidation in the common case is free.
- **Stage 6.5 draft branches on session context, not a Builder answer.** First send of the session: `Hey @skill-publishers can you please review this one: <branch-url>`. Second-or-later send (same session): the shorter `@skill-publishers remediation pushed, please re-review: <branch-url>`. Both use the `<!subteam^S08TDT143C3|skill-publishers>` group-mention syntax so every Publisher gets pinged. Group mention chosen over per-Publisher continuity for simplicity — whichever Publisher is available picks up the remediation.
- **Stage 6.6 stores channel + `thread_ts` after the first send.** `slack_send_message` is called with `thread_ts` from session context when one exists; otherwise the call omits it and the post lands top-level. The response's `ts` is captured and stored so the next same-session send threads under it. The `slack_search_channels` lookup runs only on the first send of a session — subsequent sends reuse the cached channel ID.
- **Stage 6.7's hand-off copy rewritten** to point at the same-session model: each remediation in the current session creates a fresh branch and lands as a threaded reply right under the original message; remediations started in a new session post a fresh top-level message instead.
- **Failure quick-reference grew** with one new row covering the new-session degradation case: Skill Fixer surfaces it up front when Stage 6 starts in a new session ("heads up — the remediation will land as a new top-level post; audit trail still works via GitHub issues + CI logs + the candidate branch"). No recovery action required.
- **Why same-session-only.** The earlier v0.6.0 design (in flight earlier this day) asked the Builder at "Stage 6.0" whether the submission was fresh or a continuation, and on continuation the Builder pasted the original Slack permalink so Skill Fixer could parse channel ID and `thread_ts` from it. That prompt was over-engineered: in the common case (Publisher sends back; Builder remediates in the same session), Skill Fixer already has the `thread_ts` from the first send's response. The permalink-paste path only adds value for cross-session continuation — which is itself rare and degrades cleanly to "fresh top-level post." Choosing "no prompt, accept the cross-session split" over "always prompt, occasionally help" trims the user-facing surface area and removes a class of paste-typo failure modes (mistyped permalinks, threaded-reply permalink confusion). The system-of-record audit trail (GitHub issues, candidate branch, CI logs, auto-committed `review-report.md`) is untouched by the cross-session split.
- **Why coordinated with idempotency.** Per-trigger-message idempotency in `af-skill-admin`'s CI scripts means re-applying the same 🔍 reaction to the same trigger message no longer re-runs the review pipeline — it short-circuits with a permalink to the prior bot reply. Consolidation amplifies the win: when the bot's reply lives in the same thread the trigger message belongs to, the idempotency lookup is local to that thread and always hits. The two refinements only fully pay off together.
- **README updated.** The Stage 6 summary now describes the same-session consolidation and the cross-session degradation. No structural change to the flow.
- **Backwards compatible.** Pre-v0.6 review threads continue to work — they just don't auto-thread. A Builder remediating a pre-v0.6 candidate in a new v0.6 session sees a fresh top-level post (the cross-session case), exactly the documented degradation.

## [0.5.0] — 2026-05-20

Adds `[skill].name` pattern normalization to Stage 1B (standalone discovery) and Stage 1's Bucket B catalog, and fixes a Stage 6 channel-resolution bug that would have caused every Submit-for-review run to fail.

- **Bug fix — Stage 6.6 channel resolution.** SKILL.md was instructing `slack_search_channels` to query `"ai-skills-publisher-requests"`, but the actual publisher-reviews Slack channel is `ai-github-skills`. Without this fix, every Builder reaching Stage 6.6 would see "Couldn't find the publisher-reviews channel under the name I expect" and fall back to manual posting. Discovered during the first real-Builder run (Carolina, `af-940-validator`, 2026-05-20). The constant is now `"ai-github-skills"`; if Slack renames the channel later, this single line in SKILL.md gets updated.
- **Feature — catch non-conforming skill names BEFORE submission.** ADR-001 (and `af-skill-admin create`) require every skill name to match `^skill-[a-z0-9-]+$`. `skill-publisher-framework/scripts/review.py` doesn't currently enforce the pattern, so non-conforming names pass pre-flight review and only fail at the promote step — wasting a Publisher review cycle. The first real-Builder run hit this exact failure mode: a candidate named `af-940-validator` passed 🔍 review and the Publisher's approval, then failed at 🚀 promotion. The fix moves the check upstream to where Builders work.
- **Stage 1B mechanical-finding rule added.** `[skill].name` is now checked against `^skill-[a-z0-9-]+$` during standalone discovery. Mismatch is a **Bucket B** finding (Builder picks the final name; Skill Fixer proposes a normalized candidate but doesn't decide). The proposed candidate is computed from the current value: lowercase, replace underscores with hyphens, prepend `skill-` if missing, and *note for the Builder* — don't strip automatically — any redundant company prefix (`af-`, `amf-`, `americanflat-`) since the Americanflat scope is implicit.
- **Stage 1 (remediation mode) Bucket B catalog extended.** Same name-pattern issue is listed alongside the existing `[skill].owner` / `[skill].description` / `[skill].tier` examples, so when a Publisher's send-back checklist includes the naming convention, Skill Fixer recognizes the category.
- **Stage 3 gains a name-specific prompt template.** When the name needs renaming, Skill Fixer asks the Builder with the proposed candidate inline, validates the response against the regex before accepting, and notes the redundant-prefix consideration without forcing a decision. Echo-back-typos discipline preserved.
- **Stage 4 application:** the rename is one finding that touches two files (`skill.toml [skill].name` AND `SKILL.md` frontmatter `name`). Both diffs are shown together as one finding's coordinated change. The folder name on disk is not renamed (Skill Fixer doesn't rename folders; the candidate branch in Stage 6 derives from the manifest, not the folder path).
- **Why upstream catching matters.** Even with this fix, downstream gates remain (`af-skill-admin create` still enforces the regex at promotion time). Layered enforcement: Builder catches with Skill Fixer in pre-flight; Publisher catches in human review (Stage 1.1 identity check); promote workflow catches at the gate. Each layer is cheaper to recover from than the next — Skill Fixer's catch costs the Builder ~30 seconds; Publisher's catch costs a send-back round-trip; promote's catch costs an already-approved skill's full cycle.
- **Backwards compatible.** Skills with conformant names continue to pass with zero new findings. The new check only fires when the existing name violates the pattern.

## [0.1.0] — 2026-05-04

Initial release. Sibling to `skill-publisher-framework` v0.9.1; remediates draft skills the framework sent back.

- **Five-stage flow.** Pre-flight → parse checklist → plan → gather Builder input → apply fixes → hand off. Stages run in order; the run aborts on any Bucket C finding rather than silently patching it.
- **Three-bucket triage.** Each finding from the checklist is classified A (mechanical, auto-fixable with approval), B (needs Builder input — owner, tier, description, changelog), or C (security / integrity — leaked secret, malicious-prompting, Tier 3 missing kill switch). Bucket C is escalation-only; Skill Fixer refuses to patch it.
- **No fabrication.** Owner identity, tier, description, version, and changelog content are never invented. The Builder is asked for each. If they ask for a tier suggestion, the skill refuses (mirrors the Publisher Framework's Stage 1.2 stance).
- **Per-change approval.** Each diff is shown before being written. The Builder replies `apply` or `skip` for each finding individually; Stage 2 plan-level approval is not blanket consent.
- **No local verification.** Skill Fixer never runs `skill-publisher-framework/scripts/review.py`, never reimplements the compliance checks, and never tries to predict whether the Publisher will pass the candidate — even when the framework happens to be installed on the same machine. Verification belongs to the Publisher's re-run on the Publisher's machine. This keeps the role boundary clean (Builders fix; Publishers verify) and avoids the false-confidence trap of "it passed locally, but the Publisher's machine flagged it."
- **Local-only writes, no network.** Tier 2 writes-with-notify, but with no network and no git remote operations. Skill Fixer never runs `git push`, never edits files outside the candidate folder, and never edits `skill-publisher-framework` itself.
- **No `scripts/` directory and no `setup.py`.** Skill Fixer is purely conversational — every step requires Builder judgment, and there is no deterministic helper logic that genuinely belongs in `scripts/`, nor install-time work that genuinely belongs in `setup.py`. Both omissions are supported by `skill-publisher-framework` v0.11.0, which makes `scripts/` and `setup.py` both conditional rather than always-required. The skill installs via `git clone <url> ~/.claude/skills/skill-fixer`; prereqs (Python ≥ 3.11, Git) are verified at first invocation by Claude Code. An earlier draft of this skill included a `scripts/parse_report.py` helper and a stdlib-only `setup.py` — both were removed: the parser was overengineered for an inherently flexible input (file, paste from Slack, email forward, prose typed by the Publisher), and the installer did nothing but check Python and copy files, both of which are better handled by `git clone` and Claude Code at first invocation.

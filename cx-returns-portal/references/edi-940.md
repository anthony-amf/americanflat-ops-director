# The 940 leg — verified against live Stedi, 2026-08-27

When a reship order is created in ShipStation it is transmitted to the 3PL as an
EDI **940 (Warehouse Shipping Order)**. The 3PL answers with a **945 (Warehouse
Shipping Advice)** once it ships. Both pass through Stedi, so we can confirm a
reship actually reached the warehouse instead of assuming it did.

Everything here was read off the live API, not from documentation.

## Finding transactions

- Base: `https://core.us.stedi.com`, path `/2023-08-01/transactions`
- Auth: `Authorization: <raw key>` from `STEDI_API_KEY`
- **Reachable from cloud sessions** (unlike ShipStation)

### `transaction_type` is silently ignored — filter client-side

`?transaction_type=940` does **not** filter. Asking for 940 returns 997s and
everything else. Only `businessIdentifier` filters. The real type is at:

```
item.x12.metadata.transaction.transactionSetIdentifier    # "940", "945", "850", "997"
item.direction                                            # OUTBOUND (we sent) / INBOUND (they sent)
```

A 940 is `transactionSetIdentifier == "940"` **and** `direction == "OUTBOUND"`.
Never trust a non-empty `items` array as proof of a type — see the bug below.

### Where the order number lives

A 940 carries it in `businessIdentifiers`:

```json
{"element": "W05-02", "name": "Depositor Order Number",  "value": "902003714826003"}
{"element": "W05-03", "name": "Purchase Order Number",   "value": "902003714826003"}
```

So `?businessIdentifier=<order number>` finds every transaction for that order.

## Partnership → warehouse

The partnership on the transaction names the 3PL. Observed live:

| `partnership.partnershipId` | Warehouse |
|---|---|
| `americanflat_Taylored-EAST_NJ` | New Jersey |
| `americanflat_Taylored-SC` | South Carolina |
| `americanflat_taylored` | Fontana *(inferred — the unsuffixed partnership; confirm)* |
| `americanflat-vc_Taylored-EAST-NJ` | New Jersey, Vendor Central |
| `americanflat-vc_Taylored-SC` | South Carolina, Vendor Central |
| `americanflat-vc_taylored-FON` | Fontana, Vendor Central |

This is the routing map BigQuery could not provide (`data-sources.md`): it tells
you which 3PL actually received an order, from the EDI itself.

**940s are flowing today.** A 600-transaction sample showed 26 outbound 940s to NJ,
19 to `americanflat_taylored`, 18 to SC, with matching inbound 945s. Creating an
order in ShipStation genuinely produces a 940 — the architecture works.

## Confirming a reship

```bash
python3 scripts/confirm_940.py 25402RS
```

Reports whether a 940 went out, to which warehouse, when, and whether a 945 has
come back. Run it a few minutes after creating the order: **no 940 means the
warehouse never got it**, however healthy the ShipStation order looks.

## Bug in the shipped invoice validator (not this skill)

`~/.claude/skills/yusen-invoice-validator/scripts/validate_stedi.py` sends
`transaction_type=945` and then treats a non-empty `items` array as a 945 match,
labelling it from its own request parameters rather than the response.

Because the API ignores that parameter, the query returns **every** transaction for
the order, so any order with an 850 or a 940 is reported as *shipped*.

Reproduced live on order `902003714826003`:

```
validator reports : {'found': True, 'transaction_type': '945'}
actually present  : [('850', 'INBOUND'), ('940', 'OUTBOUND')]
did it actually ship?  False
```

That order has no 945 — it was received by the warehouse and never shipped — and
the validator calls it shipped.

**Why it matters:** a Stedi order-level pass gates payment on SP/LTL invoices
(`CLAUDE.md`), so this weakens the shipping axis on invoices worth tens of
thousands. It also inflates the `found_945` counts in the summary output.

**The fix** is the rule above: read `transactionSetIdentifier` off each item and
match on it (plus `direction`), instead of trusting the request parameter. The
940 fallback has the same flaw and the same fix. `scripts/confirm_940.py` in this
skill does it correctly and can serve as the reference.

Not fixed here — that skill's canonical source is on the Mac
(`~/.claude/skills/yusen-invoice-validator/`), and changing a payment gate deserves
its own review.
